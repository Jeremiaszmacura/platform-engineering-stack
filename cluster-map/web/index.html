Networking basics

Three address ranges

Kubernetes networking is easier once you separate these three ranges. They never overlap, and each one is managed by a different component.

A pod IP changes every time the pod is recreated. A Service's ClusterIP and DNS name stay the same for as long as the Service exists. Apps should always call the Service name, never a pod IP.
North-south traffic

Gateway API: how traffic gets in

Pods and Services are reachable only from inside the cluster. Your browser gets in through one shared Gateway. Control plane and data plane

      
Envoy Gateway (the envoy-gateway pod) is the control plane. It watches Gateways, HTTPRoutes, Services and EndpointSlices through the API server. It turns them into Envoy configuration and streams that to the proxies over xDS, a gRPC API on port 18000. It also creates the proxy Deployment and Service for each Gateway, and writes status such as Accepted and Programmed back onto the objects. No request ever passes through it.

      
Envoy (the shared-gateway-proxy pods) is the data plane. Every request from your browser passes through it. Envoy only knows what the controller sent it, so a new HTTPRoute starts working a moment after you apply it, without a restart.

      
Who may attach routes. The listener accepts HTTPRoutes only from namespaces labelled shared-gateway-access: "true" (platform/namespaces.yaml). The data namespace has no such label, so a route there is rejected with NotAllowedByListeners, and TimescaleDB stays internal. The platform team controls the door, and app teams control their own routes.

      
Why Gateway API and not Ingress? This cluster used ingress-nginx until it was retired in March 2026. The Ingress API is frozen: anything beyond host and path, such as CORS, needed controller-specific annotations like nginx.ingress.kubernetes.io/enable-cors. In Gateway API those features are typed, validated fields. A CORS filter is part of the standard, so the same HTTPRoute works with any conformant implementation (Envoy Gateway, Istio, Cilium, NGINX Gateway Fabric, …).

ServiceAccounts and RBAC

      
A ServiceAccount is a pod's identity when it talks to the Kubernetes API, the same way your kubeconfig is your identity. RBAC decides what that identity may do. Here every workload has its own ServiceAccount; the table shows which ones actually get a token.

This page is an API client too


# cluster-map/k8s/cluster-map-serviceaccount.yaml
ServiceAccount  monitoring/cluster-map           # token mounted on purpose
# platform/rbac/cluster-map.yaml
ClusterRole     cluster-map  get/list/watch  nodes, pods, services, serviceaccounts, PVCs, PVs,
                                             networkpolicies, gateways, httproutes, roles, bindings
                                             # no secrets
Role            kube-system/cluster-map-kube-proxy  get configmaps "kube-proxy"
Role            monitoring/cluster-map-prometheus   get configmaps "prometheus-config"

      
Kubernetes mounts the token at /var/run/secrets/kubernetes.io/serviceaccount/token, from the kube-api-access-* volume this page uses to detect tokens. The service calls the API server at kubernetes.default.svc. The two Roles use resourceNames, so they allow reading exactly one ConfigMap each. Prometheus follows the same pattern with its own ClusterRole. Check any identity yourself:


kubectl auth can-i watch pods  --as=system:serviceaccount:monitoring:cluster-map -A   # yes
kubectl auth can-i get secrets --as=system:serviceaccount:monitoring:cluster-map -A   # no
kubectl auth can-i list pods   --as=system:serviceaccount:apps:stock-app -n apps      # no

      
Least privilege shaped this service. The Secrets table below comes from pod specs (secretKeyRef names the Secret and key), so cluster-map never needs permission to read Secrets. Granting list secrets would hand every secret value in the cluster to a pod with a web page.

      
Two ways to turn the token off. This repo sets automountServiceAccountToken: false on the ServiceAccount, so every pod using it starts without a token. You can also set the same field on a pod spec, and the pod setting wins. Without either, even a pod with no RBAC permissions carries a token an attacker could use to explore the API.

      
Vault tokens are a different kind of identity. stock-app signs in to Vault with VAULT_TOKEN, the dev root token, not with its ServiceAccount. The usual production setup is Vault's Kubernetes auth method: Vault checks the pod's ServiceAccount token and gives back a short-lived token limited to that service's path.

    

  


  

    

      Configuration
      
Secrets and ConfigMaps

      
A pod can only reference Secrets in its own namespace. That is why the same Secret name or value can appear in two namespaces: one copy for the server and one for its client. Only the keys pods reference are shown, never values.

    

    

      

        
ObjectNamespaceKeys usedConsumed byHow

        
      

    

    
These Secrets are written with stringData in plain text and committed to Git. That's fine for a dev cluster and never acceptable anywhere else. Kubernetes Secrets are only base64-encoded, and etcd stores them unencrypted unless you enable encryption at rest. In real clusters, use the External Secrets Operator, Sealed Secrets, or the Vault Agent / CSI driver.

    
Env vars filled from a Secret are read once, when the container starts. If the Secret changes, the pod keeps the old value until it restarts. A ConfigMap mounted as a volume does update inside the pod after a short delay, but most programs read their config only at start. So Kustomize adds a hash of the content to the ConfigMap's name: a changed file means a new name, a changed pod template and a new pod. Prometheus is the exception: this page reads its ConfigMap by name, so the name stays fixed and Prometheus re-reads the file itself (--config.auto-reload).

  


  

    

      State
      
Storage: real disks and scratch dirs

    

    

      

      
WaitForFirstConsumer (kind's default StorageClass) means the volume is created only after the scheduler picks a node for the pod. A local-path volume is a directory on that node, so from then on the pod can only run there. If that node goes down, the data can't move. Network storage (EBS, Ceph, NFS) avoids that.

      
A PVC outlives its pod, so deleting the pod keeps the data. It does not outlive kind delete cluster, which ./recreate-cluster.sh runs.

      
emptyDir volumes are scratch directories deleted with the pod. stock-app needs them because it runs with readOnlyRootFilesystem: true. hostPath volumes expose the node's own files: node-exporter reads /proc, /sys and / to report on the node.

      
Grafana keeps its SQLite database on an emptyDir, and its datasources and dashboards come from ConfigMaps loaded on every start, so even a new pod loses only logins. Vault has no volume at all: in dev mode it keeps everything in memory, so a restart loses every secret and the services/ and infra/ mounts. The finished vault-configure Job does not run again by itself.

Probes

      
A readiness probe decides whether a pod is listed as an endpoint of its Service, so whether it gets traffic. A liveness probe decides whether the kubelet restarts it. Select a pod on the map to see its probes. Some pods have only a readiness probe on purpose: stock-app's /health checks the database, and an outage there should not restart the app. Vault would lose every secret on a restart. cluster-map reports ready only after its informers have finished their first list.
