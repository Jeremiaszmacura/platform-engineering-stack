What the cluster says about itself

A metric tells you that something is wrong, a trace tells you where in the request, and a log tells you what exactly happened. Here the three are wired together: Prometheus scrapes metrics and sends alerts to Alertmanager, the OpenTelemetry Collector carries traces to Tempo, and Grafana shows both.

Metrics

How Prometheus finds its targets

Nobody tells Prometheus about a new service. It asks the Kubernetes API which endpoints exist and keeps those whose Service carries an annotation. Then it pulls: every 5 seconds it fetches /metrics from each pod directly.

Annotation on the ServiceEffect
prometheus.io/scrape: "true"keep this Service's endpoints as targets (the rest are dropped)
prometheus.io/job: <name>sets the job label that dashboards filter on
prometheus.io/port: "9187"scrape this port of a multi-port Service (TimescaleDB's exporter, not PostgreSQL)
prometheus.io/path: /v1/sys/metricsreplaces /metrics (Vault)

Relabel rules also copy where each series came from into namespace, pod, service and node labels: the same names trace spans carry as k8s.namespace.name, k8s.pod.name, so a metric and a trace point at the same pod. Discovery is limited to the namespaces listed in prometheus.yml, because kube-system's DNS Service carries the same annotation; a new namespace must be added there.

A second job, kubelet, discovers the nodes (role: node) and scrapes each kubelet's /metrics/resource on port 10250: CPU and memory of the node, of each pod and of each container, measured from their cgroups. These are the per-node numbers to trust, because node-exporter can't tell kind's nodes apart (why). The kubelet asks the API server whether Prometheus' token may get nodes/metrics, a permission that, unlike nodes/proxy, reaches no exec or logs. kind's kubelets serve a self-signed certificate, so this job skips TLS verification.

Instrumentation

What stock-app measures, and what it refuses to

RED for every route

  • Rate: http_requests_total by endpoint, method and status code
  • Errors: http_responses_by_status_total by status class
  • Duration: http_request_duration_seconds, a histogram
  • Probes and scrapes go to monitoring_requests_total instead, so health checks don't flatter the error rate.
  • stock_* metrics count provider calls and cache hits, misses and refreshes.

No label straight from a request

A label is a new time series per value. A symbol label would create one series per ticker anyone ever typed, and a malicious client could grow Prometheus' memory without limit. Routes are labelled by template (/instruments/{symbol}/bars), never by raw URL. An e2e test checks it.

Grafana

Dashboards as code

Grafana's datasources and dashboards are files in Git, not clicks in a UI. Kustomize turns them into ConfigMaps, Grafana mounts them and loads them on every start, so a new pod gets them back and a review shows every change.

Stock App Metrics

Availability and latency SLIs, request rate, p95, 4XX and 5XX rates, health checks and the cache-aside pipeline.

 Tracing

Rate and duration per route measured from traces, tables of recent, slow and failed requests, and whether the Collector delivers spans to Tempo.

 Infrastructure Overview

CPU and memory of each node and pod, measured by the kubelet; the Docker host as one line, from node-exporter; and how many scrape targets are down.

Provisioned dashboards are read-only in the UI: change one there, Export → Export as JSON, save it over the file and apply it. Logins and preferences live in Grafana's SQLite database on an emptyDir, so a new pod logs you out but loses nothing else.

Alerting

From a rule to an alert you can act on

Prometheus evaluates the rules in monitoring/prometheus/k8s/alerts.yml every minute. A rule whose query returns series is pending, and firing once that has lasted its for: time. Prometheus sends firing alerts to Alertmanager, which decides what reaches people. Ours has a single receiver that sends nothing, so alerts stay in its UI at alertmanager.localhost and in Grafana under Alerting → Alert groups and Silences.

AlertSeverityFires when
Watchdognonealways: if it is missing from Alertmanager, the alerting pipeline itself is broken
TargetDownwarninga target's scrape has failed for 1 minute (up == 0). A Service scaled to zero has no target, so this alert can't see it
SpansQueuedwarningthe Collector's queue for Tempo hasn't emptied for a whole minute: Tempo is unreachable and the exporter is retrying
SpansDroppedcriticalthe Collector gave up retrying (after about 5 minutes) and dropped spans; those traces are lost
Firing nowSeverityLabels

What Alertmanager adds

  • Grouping: alerts with the same group_by labels arrive as one notification; ours groups by alertname.
  • Inhibition: a worse alert hides its symptoms. SpansDropped hides SpansQueued for the same exporter.
  • Silences: mute matching alerts until a set time, with a comment, e.g. while you break something on purpose. They live on an emptyDir, so a new pod forgets them.
  • Routing: labels pick the receiver, e.g. critical to a pager, warning to a chat.

Good alerts

  • Page on symptoms users feel (errors, latency); open a ticket for causes (CPU, memory, disk).
  • Use ratios and for:, not a single bad sample: a busy CPU isn't a problem, a slow service is.
  • Give every alert a severity label and a summary; real setups add a runbook_url that says what to do.
  • Alert on your own alerting: that is what Watchdog is for.
Traces

One request, followed through everything it touches

A trace is the journey of one request, identified by a trace ID. A span is one step of it (handling the request, one SQL query, one outgoing call) with a start, a duration and attributes; spans nest. Context propagation carries the trace ID: inside a process automatically, between services in the W3C traceparent header.

StageWhat ours does
Receivers take data inaccept spans over OTLP/HTTP on 4318
Processors change itmemory_limiter refuses data before the pod runs out of memory; k8s_attributes looks up the sender's pod IP and adds namespace, pod, deployment and node
Exporters send it onforward to Tempo, queueing and retrying while Tempo is down

Why a Collector in the middle

  • Apps stay simple: they only know "send to the Collector".
  • One place for shared rules: Kubernetes metadata, dropping sensitive attributes, or keeping only slow and failed traces (tail sampling, which an app can't do because it decides before the request ends).
  • It absorbs trouble: if Tempo restarts, the Collector buffers and retries instead of every app.

Gateway or agent

Ours is a gateway: one central Deployment every app sends to. An agent is a DaemonSet, one Collector per node that apps reach locally. Large clusters often use both: agents next to the apps, forwarding to a gateway that samples and exports.

To name the pod behind a span, the Collector needs to read pods: its Role covers apps only (Identity).

Who creates the spans

Instrumentation libraries plug into what the app already uses (FastAPI, SQLAlchemy, requests) and turn every incoming request, SQL query and outgoing call into a span with standard attribute names. Manual spans cover the rest: in stock-app only the call to Yahoo, whose client has no library. Tracing lives at the app's edges; its core layers never import OpenTelemetry.

Good habits

  • Name spans by route template, not raw URL, so similar requests group together.
  • Never put secrets or personal data in attributes: many people read traces.
  • Skip noise: /health and /metrics are not traced.
  • Sample when traffic grows; here every request is kept.
Together

From a slow dot to the line that explains it

The signals share one key, the trace ID. The latency histogram stores it as an exemplar on its samples (Prometheus runs with --enable-feature=exemplar-storage), and every line stock-app's own logger writes during a request carries trace_id=<id>. uvicorn's access lines and library warnings don't.

  1. metricsOn the Stock App dashboard's p95 Latency panel, each dot is an exemplar. Click one.
  2. tracesGrafana opens that request's trace in Tempo: the waterfall shows which span was slow.
  3. logsSearch the pod's log for the same ID: kubectl logs -n apps deploy/stock-app | grep <trace_id>.

Break the trace pipeline and watch alerts fire: send traffic from traffic-generator while Tempo is gone. SpansQueued fires after a minute; about 5 minutes later SpansDropped fires and inhibits it. Silence one at alertmanager.localhost (New Silence), then bring Tempo back.

kubectl scale deploy/tempo -n monitoring --replicas=0
kubectl exec -n monitoring deploy/alertmanager -- amtool alert query --alertmanager.url=http://localhost:9093
kubectl scale deploy/tempo -n monitoring --replicas=1

Interview check

Questions to answer from this chapter

Prometheus pulls; OTLP pushes. What are the trade-offs?

Pull gives a free health signal (up), central control of rate and targets, and no client buffering; it needs service discovery and network reach to every target. Push suits short-lived jobs, clients behind NAT, and events like spans; the receiver then needs back-pressure, which is why the Collector has memory_limiter.

Why compute p95 from a histogram, and why with rate()?

Histogram buckets can be summed across pods and then turned into a quantile; a client-side summary's quantiles can't be averaged. rate() over the cumulative buckets gives the distribution of the last window instead of since the process started. The result is an estimate within the bucket bounds.

What is label cardinality and how do you keep it bounded?

Every unique label combination is a series in memory. Only label with values from a small, known set (status class, route template, provider); never user IDs, raw URLs or anything a client controls. Watch prometheus_tsdb_head_series.

Which SLIs would you define for stock-app, and what SLO?

Availability: share of non-5XX responses; latency: share of requests under 1 s. Both are on the Stock App dashboard. An SLO like 99.5% over 30 days gives an error budget; alert on its burn rate (fast and slow windows), not on single errors.

Why is Alertmanager a separate service from Prometheus?

Prometheus only decides that a condition holds. Grouping, inhibition, silences and routing need one shared place: teams run several Prometheus servers, often two identical ones for availability, and all send to the same Alertmanagers, which de-duplicate their alerts so a person is told once.

A silence or an inhibition: which one when?

A silence is a person muting known alerts for a while, such as during maintenance; it expires by itself. An inhibition is a standing rule in the config: while one alert fires, the alerts it causes stay hidden.

Why not let every app send traces straight to Tempo?

Then every app owns retries, batching, metadata and backend choice. A Collector centralizes that: tail sampling, attribute scrubbing, k8s metadata, fan-out to two backends, and a backend change without redeploying apps.
