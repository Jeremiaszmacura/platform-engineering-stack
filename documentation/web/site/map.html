Where everything runs

In a production cluster each node is its own machine, for example an EC2 instance on AWS. Only in this local test cluster is each node a Docker container on your machine. Each chip, a small box inside a node, is a pod, coloured by namespace. Select a pod to see its pod IP, its Service's virtual IP, its identity and secrets. Three kinds of IP address explains how the two IPs differ. Lines show who it talks to: solid for calls it makes, dashed for calls it receives.

Reading the chips

  • Dashed chips use hostNetwork: they share the node's IP instead of getting their own.
  • Faded chips are finished Job pods. They stay until something deletes them.
  • An orange dot means the pod runs but is not ready, so its Services don't send it traffic.
  • The grey line under each node lists its node agents: one kube-proxy and one kindnet pod per node.

Watch it change

The map refreshes every 5 seconds and new pods flash. Scale something or delete a pod, then watch the scheduler place the replacement:

kubectl scale deploy/traffic-generator -n apps --replicas=3
kubectl delete pod -n apps -l app=stock-ui
Scheduling

Why a pod lands where it does

The scheduler first filters out nodes a pod can't use, then scores the rest. Three rules shape this cluster.

Taints keep pods off

The control-plane node carries the taint node-role.kubernetes.io/control-plane:NoSchedule. Only pods that tolerate it run there: the static control-plane pods, the per-node agents, CoreDNS, local-path-provisioner, and node-exporter, whose DaemonSet adds the toleration on purpose.

Volumes pin pods

A local-path volume is a directory on one node, so its PersistentVolume has a node affinity. TimescaleDB can only ever run on that node: State & storage shows the chain.

Nothing guarantees spread

No pod here asks to be spread out (topology spread constraints or anti-affinity), so with more replicas two can land on the same worker, and losing that node takes both.

Questions to answer from this page

What is a "node" in this cluster, physically?

In a production cluster a node is a virtual or physical machine. On AWS it is an EC2 instance in a VPC subnet, and its node IP is a VPC address. This cluster is a local test environment that simulates that: kind runs each node as a Docker container with systemd, containerd and the kubelet, from the kindest/node image. The three containers sit on Docker's kind bridge network, so here node IPs are Docker addresses. Nothing above the kubelet changes.

A pod shows Running but not Ready. What happens to its traffic?

The EndpointSlice controller marks its endpoint not ready in every Service it backs, so kube-proxy and Envoy stop sending it new connections. The kubelet does not restart it. Only a failing liveness probe would.

Why does node-exporter run on the control-plane node when stock-app can't?

The control-plane node is tainted NoSchedule. node-exporter's DaemonSet tolerates that taint so every node is monitored. stock-app's Deployment doesn't, so the scheduler filters that node out.

Two replicas of an app landed on the same worker. How do you prevent it?

Add a topologySpreadConstraints entry on kubernetes.io/hostname with maxSkew: 1 (or pod anti-affinity), and a PodDisruptionBudget so a node drain keeps one running.
