Learn · identity and secrets

Who may do what, and with which secret

Every pod runs as an identity, reads configuration and maybe a secret, and can reach other pods. Least privilege means each of those is as small as the job allows. This chapter shows how small they are here, live, and where they are not.

ServiceAccounts and RBAC

Who may talk to the Kubernetes API

A ServiceAccount is a pod's identity towards the API, the way your kubeconfig is yours. RBAC decides what it may do. Every workload here has its own ServiceAccount with automountServiceAccountToken: false, so it gets no token at all. Only the identities on the left of this diagram mount one, each for a reason.

ServiceAccountNamespaceUsed byautomountTokenPermissions

Two ways to switch the token off

Set automountServiceAccountToken: false on the ServiceAccount (this repo's default, so every pod using it starts without a token), or on the pod spec, which wins. Without either, even a pod with no RBAC permissions carries a token an attacker could use to explore the API.

Least privilege, by design

The OpenTelemetry Collector gets a Role in apps, not a ClusterRole: it can't see any other namespace. This site's two extra Roles use resourceNames, so each allows reading exactly one ConfigMap. Of the project's workloads, only Vault may read a Secret: its own unseal key (below).

An API client

How this site reads the cluster

Every diagram on this site comes from the documentation service. It doesn't list the cluster for each page view: client-go informers list each kind of object once, then keep a watch open, so an in-memory copy follows the cluster within about a second. Controllers and operators use the same mechanism. Only two small ConfigMaps (kube-proxy, prometheus-config) are read with a GET on each map request.

# documentation/k8s/documentation-serviceaccount.yaml: token mounted on purpose
ServiceAccount  docs/documentation
# platform/rbac/documentation.yaml
ClusterRole     documentation  get/list/watch  nodes, pods, services, serviceaccounts, PVCs, PVs,
                                               networkpolicies, gateways, httproutes, roles, bindings   # no secrets
Role            kube-system/documentation-kube-proxy   get configmaps "kube-proxy"          # the pod range
Role            monitoring/documentation-prometheus    get configmaps "prometheus-config"   # the scrape namespaces

Least privilege shaped this service. The Secrets table below comes from pod specs: secretKeyRef names the Secret and the key, so the site never needs to read a Secret. Granting list secrets would hand every secret value in the cluster to a pod that serves a public web page.

Configuration

Secrets and ConfigMaps

A pod can only reference Secrets in its own namespace, which is why the same value appears twice: once for the server and once for its client (the database password in data and in apps). Only key names are shown here, never values.

ObjectNamespaceKeys usedConsumed byHow

These Secrets are written with stringData in plain text and committed to Git. Fine for a laptop cluster, never anywhere else: Secrets are only base64-encoded, and etcd stores them unencrypted unless encryption at rest is on. Real clusters use the External Secrets Operator, Sealed Secrets or the Vault Agent / CSI driver.

An environment variable filled from a Secret is read once, when the container starts: a changed Secret needs a restart. A mounted ConfigMap does update in the pod, but most programs read config only at start, so Kustomize puts a hash of the content in the ConfigMap's name and a change rolls out new pods (Workloads).

Vault

How a service signs in to Vault

HashiCorp Vault holds the apps' own secrets in two KV v2 mounts (how it starts): services/, one path per service, and infra/, reserved. No app holds a Vault password. Each signs in with its ServiceAccount through Vault's built-in kubernetes auth method and gets a short-lived Vault token that opens only its own path. These steps follow stock-app; the documentation service does the same to keep the GitHub token of the reader who comments (how).

  1. kubeletMounts a token for stock-app's ServiceAccount at /var/run/secrets/vault/token, issued for the audience vault, and replaces it before its hour is up. The Kubernetes API rejects tokens issued for another audience, so the pod still has no API access.
  2. stock-appSends that token to Vault with the role stock-app.
  3. vaultAsks the Kubernetes API whose token it is (a TokenReview). The role accepts only ServiceAccount stock-app in apps, with the audience vault.
  4. vaultReturns a Vault token valid for one hour, with the policy stock-app: read and write services/stock-app/*, a 403 anywhere else.
  5. stock-appUses that token for every request, and signs in again when Vault rejects it (expired). Vault stores its tokens, so a restart doesn't invalidate them.
# stock-app/k8s/stock-app-deployment.yaml: the pod's token, for Vault only
projected serviceAccountToken   audience: vault   expirationSeconds: 3600   → /var/run/secrets/vault/token
# platform/rbac/vault.yaml: Vault may check tokens and keep its unseal key, nothing else
ClusterRoleBinding vault-tokenreview   ServiceAccount vault/vault → ClusterRole system:auth-delegator
RoleBinding vault/vault-unseal-key     ServiceAccount vault/vault → create secrets, get secret "vault-unseal-key"
# vault/k8s/configure-vault.sh and stock-app-policy.hcl: set up again on every Vault start
role    auth/kubernetes/role/stock-app   ServiceAccount apps/stock-app   audience vault   TTL 1h   policy stock-app
policy  stock-app                        create, read, update on services/data/stock-app/*
role    auth/kubernetes/role/documentation   ServiceAccount docs/documentation   audience vault   TTL 1h   policy documentation
policy  documentation                    create, read, update on services/data/documentation/*

The root token, root, is only for people at vault.localhost and for Vault's start-up hook. A token stolen from stock-app is worth little: the ServiceAccount token works only with Vault, and the Vault token only on stock-app's path, for an hour at most.

The unseal key is a Kubernetes Secret. Vault's start-up hook saves it as vault-unseal-key in namespace vault (how). Of the project's workloads only Vault's ServiceAccount may read it; RBAC can't limit create to one name, so Vault may also create other Secrets there. Cluster admins, Kubernetes' own controllers, Envoy Gateway's controller, which reads Secrets in every namespace for TLS certificates, and cert-manager, which writes them, can read it too, and etcd keeps it unencrypted (the fix).

Sign in as stock-app yourself and see which policies the Vault token carries.

JWT=$(kubectl create token stock-app -n apps --audience vault)
curl -s http://vault.localhost/v1/auth/kubernetes/login -d "{\"role\":\"stock-app\",\"jwt\":\"$JWT\"}" | jq .auth.policies

Write a secret through stock-app, then read it back.

curl -X POST http://stock.localhost/secret -H 'Content-Type: application/json' -d '{"key":"demo","value":"x"}'
curl http://stock.localhost/secret/demo
TLS and certificates

How a server proves who it is

TLS encrypts a connection and lets the client check who answered. The server sends its certificate: the hostnames it may serve, its public key and the signature of a certificate authority (CA). The client accepts it only if a CA it already trusts signed it and the hostname it asked for is listed, and the server proves in the handshake that it holds the matching private key. In mutual TLS (mTLS) the client sends a certificate too. These are the certificates in your cluster; kind and Envoy Gateway made all but the last on their own.

ca.crt: trusting the API server

kubeadm created the Kubernetes CA with the cluster (valid 10 years; the certificates it signed, 1 year). Kubernetes copies it into the ConfigMap kube-root-ca.crt in every namespace, and the kubelet mounts it as ca.crt with the token. This site, Prometheus and Vault's hook check the API server with it.

A token is not a certificate

The certificate proves the server to the pod; the ServiceAccount token proves the pod to the server. The token is a JWT the API server signs with its private key (sa.key). Anyone can check the signature with the public key (published at /openid/v1/jwks), but only the API server knows if the token is still valid, for example that its pod still exists. A TokenReview asks it, as Vault does (above).

How a node gets its certificate

A joining node's kubelet sends a CertificateSigningRequest (CSR) with a bootstrap token; the controller manager approves and signs it, and the kubelet renews it the same way before it expires. kubectl get csr lists these requests.

How the Gateway gets its HTTPS certificate

  1. cert-managerThe ClusterIssuer selfsigned signs the CA certificate sample-cluster CA with its own key, into the Secret sample-cluster-ca. Nobody trusts a self-signed CA until they choose to.
  2. cert-managerThe ClusterIssuer sample-cluster-ca signs certificates with that CA's key.
  3. cert-managerThe Certificate shared-gateway-tls lists every *.localhost hostname. cert-manager creates a private key, has the certificate signed and writes both into the Secret shared-gateway-tls.
  4. envoyThe Gateway's https listener on 443 names that Secret. Envoy decrypts each request (TLS termination) and forwards it as plain HTTP to the pod, so apps need no certificate.
  5. cert-managerThe certificate lasts 24 hours. After 16, cert-manager writes a new one into the same Secret, and Envoy switches to it without a restart.
# platform/cert-manager/cluster-ca.yaml: the cluster's own CA
ClusterIssuer selfsigned           selfSigned
Certificate   sample-cluster-ca    isCA: true, issuer selfsigned → Secret sample-cluster-ca
ClusterIssuer sample-cluster-ca    ca: Secret sample-cluster-ca
# platform/gateway/: the Gateway's certificate and listener
Certificate   shared-gateway-tls   issuer sample-cluster-ca, 24h, docs.localhost, grafana.localhost, …
Gateway       shared-gateway       listener https :443, tls: Terminate, Secret shared-gateway-tls

Your machine doesn't trust this CA, so browsers warn and curl refuses until you pass or trust it, and every ./recreate-cluster.sh makes a new one. A CA you trust can sign a certificate for any name, your bank's too, and its key is a Secret any cluster admin can read: remove it from your keychain when you are done. Plain http:// keeps working.

Why cert-manager? It is how most clusters get certificates. The same Certificate with an ACME issuer such as Let's Encrypt gets a publicly trusted certificate for a real domain, renewed the same way.

Save the CA, then call a service over HTTPS without it and with it.

kubectl get secret sample-cluster-ca -n cert-manager \
  -o jsonpath='{.data.ca\.crt}' | base64 -d > sample-cluster-ca.crt
curl -sS https://docs.localhost        # fails: unable to get local issuer certificate
curl --cacert sample-cluster-ca.crt -sI https://docs.localhost   # HTTP/2 200: over TLS, Envoy speaks HTTP/2

Read the certificate Envoy sends: hostnames, issuer and expiry.

openssl s_client -connect 127.0.0.1:443 -servername grafana.localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -text | grep -E 'Issuer:|Not (Before|After)|DNS:'

Delete the Secret: cert-manager signs a new certificate within seconds, and HTTPS fails until it does. A real renewal updates the Secret in place, with no gap.

kubectl delete secret shared-gateway-tls -n envoy-gateway-system
kubectl get certificate -A    # READY is True again; openssl above shows new dates

The certificates kubeadm made, and the nodes' certificate requests.

docker exec sample-cluster-control-plane kubeadm certs check-expiration
kubectl get csr

Trust the CA on macOS (Chrome and Safari), and remove it again.

sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain sample-cluster-ca.crt
sudo security delete-certificate -c "sample-cluster CA" /Library/Keychains/System.keychain
Pod security

How locked down each pod is

The Pod Security Standards define three levels: privileged (anything goes), baseline (no host namespaces, no privileged containers, no dangerous capabilities) and restricted (non-root, no privilege escalation, all capabilities dropped, a seccomp profile). Kubernetes enforces them per namespace with a label. This scorecard checks every workload pod against restricted, plus two habits this repo cares about: a read-only root filesystem and resource limits.

PodNamespaceNon-rootNo escalationDrops ALLSeccompHost accessRead-only rootLimitsRestricted

Most failures are one missing line: seccompProfile: {type: RuntimeDefault} on the pod. The others are real trade-offs: the TimescaleDB and Vault images start as root and drop to postgres and vault themselves; node-exporter needs the host's network and process table to report on the node.

Network isolation

Who may connect to whom

Without a NetworkPolicy every pod can open a connection to every other pod: stock-ui could reach TimescaleDB on 5432, and only the password stands in the way. kindnet enforces NetworkPolicy, so you can practise here.

Exercise: lock down the database

Deny all ingress in data, then allow only stock-app from apps on 5432. Remember Prometheus scrapes the exporter on 9187, so allow that too, or the timescaledb target goes down.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: timescaledb-ingress, namespace: data}
spec:
  podSelector: {matchLabels: {app: timescaledb}}
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: apps}}
          podSelector: {matchLabels: {app: stock-app}}
      ports: [{port: 5432, protocol: TCP}]
    - from:
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: monitoring}}
          podSelector: {matchLabels: {app: prometheus}}
      ports: [{port: 9187, protocol: TCP}]
Hands on

Try it

Ask the API what an identity may do: this site may watch pods, may not read Secrets; stock-app may do nothing.

kubectl auth can-i watch pods  --as=system:serviceaccount:docs:documentation -A   # yes
kubectl auth can-i get secrets --as=system:serviceaccount:docs:documentation -A   # no
kubectl auth can-i list pods   --as=system:serviceaccount:apps:stock-app -n apps  # no
kubectl auth can-i --list      --as=system:serviceaccount:monitoring:prometheus

Confirm a ServiceAccount hands out no token, and that the pod has no token volume.

kubectl get sa stock-app -n apps -o yaml
kubectl get pod -n apps -l app=stock-app -o jsonpath='{.items[0].spec.volumes[*].name}'

Ask the API server which pods the restricted profile would reject, without enforcing anything (a server-side dry run prints warnings).

kubectl label --dry-run=server --overwrite ns apps data vault monitoring docs pod-security.kubernetes.io/enforce=restricted

Static · secrets

Plain · TLS

Inside the cluster, traffic is unencrypted

Skipped · TLS

Each kubelet signs its own serving certificate, so no CA can vouch for it and the kubelet job sets insecure_skip_verify.

Exercise: set serverTLSBootstrap: true in kind's kubeadm config, approve the kubernetes.io/kubelet-serving CSRs, and give Prometheus the cluster CA as ca_file.

Interview check

Questions to answer from this chapter

How does a pod authenticate to the Kubernetes API, and how would you stop it from being able to?

The kubelet mounts a short-lived, audience-bound ServiceAccount token (a projected volume, kube-api-access-*) plus the cluster CA; the client sends it as a Bearer token and RBAC authorizes the system:serviceaccount:<ns>:<name> user. Stop it with automountServiceAccountToken: false on the ServiceAccount or the pod, and by binding no roles.

Role versus ClusterRole, RoleBinding versus ClusterRoleBinding: which combinations exist?

A Role grants within one namespace; a ClusterRole defines rules that can be cluster-wide. A RoleBinding grants a Role or a ClusterRole inside its namespace; a ClusterRoleBinding grants a ClusterRole everywhere. Binding a ClusterRole with RoleBindings is the usual way to reuse one set of rules in a few namespaces.

How can a pod sign in to Vault without a stored password?

With its ServiceAccount token, through Vault's kubernetes auth method. Vault checks the token with the API's TokenReview (Vault needs system:auth-delegator), matches its ServiceAccount, namespace and audience to a role, and returns a short-lived Vault token with that role's policies. A projected token with its own audience keeps the token useless against the Kubernetes API.

Why are Kubernetes Secrets "not secret", and what do you use instead?

They are base64, readable by anyone with get secrets in the namespace (or who can create a pod there and mount it), and stored in etcd in the clear unless encryption at rest is configured. Use an external store (Vault, a cloud secret manager) with the External Secrets Operator or a CSI driver, keep RBAC on Secrets tight, and turn on etcd encryption with a KMS provider.

What do the Pod Security Standards' restricted profile require, and how are they enforced?

Run as non-root, allowPrivilegeEscalation: false, drop ALL capabilities (only NET_BIND_SERVICE may be added back), a RuntimeDefault or Localhost seccomp profile, no host namespaces or hostPath, and only safe volume types. The built-in Pod Security Admission enforces a level per namespace through pod-security.kubernetes.io/enforce, with warn and audit modes to roll it out gently.

Two NetworkPolicy from entries: when is it AND, when is it OR?

Selectors in the same list item (a namespaceSelector and a podSelector together) must both match: AND. Separate list items are alternatives: OR. Policies are additive allow-lists; once any policy selects a pod for ingress, everything not allowed is denied.

What does a client check before it trusts a server's certificate?

That a CA in its trust store signed it, directly or through intermediates; that the hostname it connected to is in the certificate's names; and that today is between its notBefore and notAfter. In the handshake the server then proves it holds the private key. A self-signed certificate passes only if the client trusts that exact certificate.

A certificate expired and the cluster stopped working. Where do you look?

On kubeadm clusters the control plane's certificates last one year: kubeadm certs check-expiration shows them, kubeadm certs renew all and a restart of the control-plane pods fixes them, and every kubeadm upgrade renews them. Kubelets renew their client certificates themselves through CSRs. cert-manager renews at two thirds of a certificate's life; alert on certmanager_certificate_expiration_timestamp_seconds in case it can't.

TLS at a gateway: terminate or pass through?

Terminate (this cluster): the gateway holds the certificate, decrypts, routes by HTTP host and path, applies filters such as CORS, and forwards plain HTTP or encrypts again to the backend. Passthrough (a TLSRoute): the gateway routes encrypted bytes by the hostname in the handshake (SNI), and only the backend holds the certificate and sees HTTP.

How do pods get mTLS with each other, tied to their ServiceAccounts?

With a service mesh such as Istio or Linkerd. It gives each pod a short-lived certificate whose identity is its ServiceAccount (spiffe://cluster.local/ns/apps/sa/stock-app), and its proxy does mTLS for the app, so the code doesn't change. Policies can then allow callers by ServiceAccount instead of by IP.
