Learn · state and storage

What survives a restart

Pods are disposable; data is not. Every component here keeps its state somewhere different, from a persistent volume to plain memory, and each choice decides what is lost when a container restarts, a pod is replaced or the cluster is rebuilt.

The matrix

Where each piece of state lives

A container restart (crash, OOM kill, failed liveness probe) keeps the pod and its volumes. A deleted pod gets a replacement with fresh emptyDirs. ./recreate-cluster.sh deletes the whole cluster: only what is in Git comes back.

Vault is the sharp edge: an OOM kill or a node restart quietly empties it. Its mounts, auth method and policies are back before the pod turns ready (how) and stock-app signs in again by itself, so its secret API keeps working, but every secret written before is gone.

Persistent volumes

From a claim to a directory on a node

A pod asks for storage with a PersistentVolumeClaim. The StorageClass decides how a PersistentVolume is made to satisfy it. kind's default class, standard, uses the local-path provisioner: the volume is a directory on one node. This is the chain in your cluster:

WaitForFirstConsumer

The class creates the volume only after the scheduler has picked a node for the pod, so the directory lands where the pod runs. From then on the PV's node affinity pins the pod to that node. If the node goes away, the data can't follow. Network storage (EBS, Ceph, NFS) doesn't have that limit.

Reclaim policy and retention

The class's reclaim policy is Delete: deleting the PVC deletes the directory. The StatefulSet's PVC retention policy is Retain: deleting or scaling down the StatefulSet keeps the claim, so recreating it finds the same data.

Controllers

Why TimescaleDB is a StatefulSet

Stable name

The pod is always timescaledb-0, not a random hash, and keeps that name across restarts. Kubernetes requires the StatefulSet's serviceName to be a headless Service (clusterIP: None): timescaledb-headless gives the pod its own DNS name, timescaledb-0.timescaledb-headless.data. Clients use timescaledb-service, a normal ClusterIP Service.

Its own volume

volumeClaimTemplates gives each replica its own PVC (data-timescaledb-0) that follows the pod across restarts. A Deployment's replicas would all share one claim.

Order

Replicas start one after another and stop in reverse, which clustered databases need. A second replica would not make PostgreSQL highly available by itself: replication is the database's job.

Application state

stock-app's cache-aside

stock-app answers from TimescaleDB and calls Yahoo Finance only when a request reaches outside the dates it has synced: one instrument lookup, then one call for the bars of a single date range. TimescaleDB is a cache that can be thrown away: an empty database after ./recreate-cluster.sh just means the first requests are slower.

Scratch space

emptyDir and hostPath

An emptyDir is a scratch directory that lives as long as the pod. stock-app needs two because it runs with readOnlyRootFilesystem: true: /tmp, and a home directory where yfinance caches time zones. A hostPath exposes the node's own files: node-exporter reads /proc, /sys and / to report on the node, which is also why it fails the restricted pod security profile.

Hands on

Try it

Follow the chain yourself: claim, volume, and the node it is pinned to.

kubectl get pvc,pv -A
kubectl get pv -o jsonpath='{.items[0].spec.nodeAffinity}'

Delete the database pod: it comes back with the same name, on the same node, with the same data.

kubectl delete pod timescaledb-0 -n data
kubectl get pod timescaledb-0 -n data -o wide --watch

Look inside the cache: one row per symbol with the window it has synced.

kubectl exec -it timescaledb-0 -n data -c timescaledb -- psql -U stockapp -d stockdata \
  -c 'SELECT symbol, first_synced_date, last_synced_date FROM instruments;'

What to fix next

Ephemeral · secrets

Vault keeps everything in memory

Dev mode has no storage, so a restart loses every secret; only the setup in its postStart hook comes back.

Exercise: run Vault with Raft storage on a PVC and initialise it once. A restart then seals Vault instead of emptying it; the hook skips mounts that exist but waits only 60 seconds, so add auto-unseal.

No backups · data

Nothing backs up TimescaleDB

The data can be refetched, but a real database would need backups and a tested restore.

Exercise: a CronJob that runs pg_dump to a second PVC every night, then restore it into a fresh cluster. Time how long the restore takes: that is your recovery time.

Pinned · node

The database can only run on one node

Its local-path volume pins it. Drain that node and TimescaleDB stays Pending.

Exercise: kubectl drain the node (see Cluster map), watch the pod hang, then uncordon. Explain what a CSI driver with network storage would change.

Interview check

Questions to answer from this chapter

PV, PVC, StorageClass: who creates which, and when?

The app team writes the PVC (or a StatefulSet's volumeClaimTemplates). A provisioner, chosen by the StorageClass, creates a PV to match it: here when the first pod using the claim is scheduled (WaitForFirstConsumer). The cluster admin owns the StorageClass: provisioner, parameters, reclaim policy, binding mode and whether volumes can grow.

Deployment or StatefulSet for a database, and why?

A StatefulSet: stable names and network identities, one PVC per replica that follows the pod, and ordered start and stop. Even then, high availability comes from the database's own replication (or an operator such as CloudNativePG), not from the StatefulSet.

What happens to an emptyDir when the container crashes? When the pod is evicted?

A crashed container restarts in the same pod and finds the emptyDir intact. An evicted or deleted pod is replaced by a new pod with new, empty emptyDirs. Use an emptyDir with medium: Memory for fast scratch space, and count it against the memory limit.

What is cache-aside, and what can go wrong with it?

The app reads the cache first and, on a miss, loads from the source and fills the cache. Risks: stale data (here bounded by the staleness window for today's bar), a thundering herd of misses for the same key, and a slow source making every miss slow, which the traces show as the Yahoo span.
