How a request finds its pod

Traffic moves in three directions: incoming traffic enters the cluster from outside, in-cluster traffic goes from pod to pod, and outgoing traffic leaves the cluster for the internet. This chapter follows each one hop by hop, with the addresses your cluster uses right now.

Basics

Three kinds of IP address

Every IP address in a cluster is one of three kinds, and each kind comes from somewhere else and behaves differently. Node and pod IPs belong to real network interfaces; a Service IP belongs to none. An address is never two kinds at once, so their ranges must not overlap with each other or with networks the pods need to reach. The cards show the ranges of this cluster.

A pod IP changes every time the pod is recreated. A Service's ClusterIP and DNS name last as long as the Service. Apps call the Service name, never a pod IP.

Why a NodePort?

On a cloud the Gateway's Service would be type: LoadBalancer with an external IP. kind has no load balancer, so platform/gateway/envoyproxy.yaml makes it a NodePort with a fixed port, and kind publishes that one port. A NodePort is open on every node, so a rescheduled Envoy pod keeps answering; CI restarts the proxy to prove it.

Why Envoy skips the ClusterIP

Envoy Gateway watches the backend Service's EndpointSlice and hands Envoy the ready pod IPs over xDS. Envoy balances across them itself (and could retry or eject a bad one), instead of letting kube-proxy pick a pod blindly behind a second NAT.

Gateway API

Who decides where traffic goes

Pods and Services are reachable only from inside the cluster. Your browser gets in through one shared Gateway. Gateway API describes it with three kinds of objects, each owned by a different role. This is the tree in your cluster right now; a rejected route turns red.

A controller is a program running in the cluster, usually a Deployment, that watches some kinds of objects through the Kubernetes API, changes the real world until it matches them and writes the result into each object's status. Kubernetes itself is built from controllers: the Deployment controller creates ReplicaSets, and they create pods (Workloads). A Gateway API object is only data until a controller acts on it; here that controller is Envoy Gateway.

A GatewayClass says which controller acts on a Gateway, the way a StorageClass says who creates a volume. Ours names controllerName: gateway.envoyproxy.io/gatewayclass-controller; every controller ignores Gateways of other classes, so one cluster can run several. The class has no network layer of its own: a Gateway's listeners and the kinds of route attached to it decide. HTTPRoute and GRPCRoute work at layer 7 (HTTP: hostnames, paths, headers); TCPRoute, UDPRoute and TLSRoute at layer 4 (addresses and ports). This cluster uses only HTTP.

Control plane: Envoy Gateway

The envoy-gateway pod watches Gateways, HTTPRoutes, Services and EndpointSlices, turns them into Envoy configuration and streams it to the proxies over xDS (gRPC, port 18000). It creates the proxy Deployment and Service for each Gateway and writes status back: Programmed on the Gateway, Accepted and ResolvedRefs on each route. No request passes through it.

Data plane: Envoy

The shared-gateway-proxy pods. Every request from your browser passes through them. Envoy only knows what the controller sent, so a new route works a moment after kubectl apply.

Who may attach. The listener admits HTTPRoutes only from namespaces labelled shared-gateway-access: "true" (platform/namespaces.yaml). data has no label, so a route there is rejected with NotAllowedByListeners and TimescaleDB can't be exposed by accident. The platform team controls the door; app teams control their own routes.

Why Gateway API and not Ingress? The Ingress API is frozen: anything beyond host and path, such as CORS, needed controller-specific annotations like nginx.ingress.kubernetes.io/enable-cors. Gateway API makes those typed, validated fields, splits the platform's part (Gateway) from each app's part (HTTPRoute), and any conformant implementation (Envoy Gateway, Istio, Cilium, NGINX Gateway Fabric) runs the same core routes. CORS is an Extended feature, so an implementation may leave it out. This cluster used ingress-nginx until it moved over.

Cross-origin

CORS: the call your browser makes

stock-ui needs prices from stock-app. The stock-ui pod never calls the API: it only serves files. The JavaScript runs in your browser, and the browser calls http://stock.localhost from the origin http://stock-ui.localhost.

  • The filter (a standard HTTPRoute field since Gateway API v1.5) allows exactly two origins, stock-ui and traffic-generator, and only GET.
  • A plain GET is a "simple" request: no preflight. A custom header or a PUT makes the browser ask first with OPTIONS, and Envoy answers that itself.
  • For any other origin Envoy adds no Access-Control-Allow-Origin, so the browser hides the response from the page. The server still answered: CORS protects users, it doesn't hide your API.
In-cluster traffic

Pod to Service to pod

stock-app runs a query against TimescaleDB. In-cluster traffic never touches the Gateway: DNS turns the name into a ClusterIP, and kube-proxy's NAT rules on the sending node turn that into a pod IP.

With two replicas the first KUBE-SVC rule matches with -m statistic --mode random --probability 0.5

What to fix next

    
Acceptable on a laptop, and each one is a good exercise. The first is checked live.

  

  

    

    
Open · TLS
Everything is plain HTTP

      
The Gateway has one HTTP listener, so Grafana logins and the Vault token cross the network unencrypted.

      
Exercise: add an HTTPS listener on 443 with a self-signed certificate Secret
        (tls.certificateRefs), publish its nodePort in kind-cluster.yaml, and redirect HTTP to
        HTTPS with a RequestRedirect filter.

    
Open · limits
No rate limits and only the default timeout at the edge

      
Any client can open as many requests as it likes, and Envoy ends a request after its default 15 s route timeout and answers 504, even if the app is still working.

      
Exercise: set an explicit request timeout that fits stock-app on stock-app-route (timeouts.request) and a
        local rate limit with Envoy Gateway's BackendTrafficPolicy; fire traffic-generator at it.

  






  
Interview check
Questions to answer from this chapter

  

    
Walk me through what happens when I open http://stock-ui.localhost.

      
The name resolves to 127.0.0.1; Docker forwards host :80 to the control-plane container's :30080; kube-proxy's
      NodePort rule DNATs it to an Envoy pod; Envoy matches the Host header to stock-ui-route and connects to a
      ready stock-ui pod IP from the EndpointSlice; kindnet routes the packet to that pod's node; nginx answers.

    
ClusterIP, NodePort, LoadBalancer: which does this cluster use where, and why?

      
Every app Service is ClusterIP: only reachable inside. The Gateway's proxy Service is a NodePort with a fixed port,
      because kind has no cloud load balancer and kind can publish one fixed port. On a cloud it would be a LoadBalancer.
      Apps never get NodePorts: one entry point, one place for TLS, auth and limits.

    
A new HTTPRoute doesn't work. How do you debug it?

      
kubectl describe httproute: Accepted: False with NotAllowedByListeners means the
      namespace lacks the label; NoMatchingListenerHostname means the hostname isn't under *.localhost;
      ResolvedRefs: False means the backend Service or port is wrong. Then check the EndpointSlice has ready
      pods, and Envoy's /clusters. curl -H 'Host: x.localhost' 127.0.0.1 takes DNS out of the picture.

    
How does kube-proxy load-balance a ClusterIP, and what are its limits?

      
In iptables mode, random-probability rules (1/n, 1/(n-1), …; the last rule has none) pick a pod per new connection.
      They know nothing about load or health beyond readiness, and long-lived connections stick to one pod. nftables mode
      scales better (IPVS is deprecated since 1.35);
      L7 balancing (per request, with retries) needs a proxy such as Envoy or a service mesh.

    
What does ndots:5 cost, and how would you reduce it?

      
Names with fewer than five dots try every search domain first, so query1.finance.yahoo.com costs three
      NXDOMAIN answers before the real lookup. Use fully qualified names with a trailing dot, lower ndots in the
      pod's dnsConfig, or run NodeLocal DNSCache to make the misses cheap.

    
Why put CORS on the route instead of in the app, and what is the trade-off?

      
One typed, validated place that a gateway supporting the Extended CORS feature implements; preflights never reach the app; the policy is
      visible in the manifest. The trade-off: changing allowed origins is a route change, and a request that bypasses the
      Gateway (pod to pod) gets no CORS, which is fine because only browsers enforce it.
