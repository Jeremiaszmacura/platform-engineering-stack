Learn · workloads

How pods are started, checked and replaced

Nobody here creates a pod by hand. Controllers do: each workload kind promises something different, and the kubelet keeps every pod honest with probes. This chapter shows which promise each component relies on, and what happens between kubectl apply and a pod taking traffic.

Health

Probes: ready is not alive

The kubelet runs each container's probes. A failing readiness probe takes the pod out of its Services' endpoints, so it gets no new traffic, and nothing restarts. A failing liveness probe restarts the container. Mixing them up turns a database blip into a restart storm.

ComponentReadinessLivenessReadyRestarts
  • stock-app has only a readiness probe on purpose: /health checks the database, and a database outage must not restart the app, which couldn't fix it anyway.
  • Vault has no liveness probe: in dev mode a restart wipes every secret.
  • documentation reports ready only after its informers finished their first list, so it never serves an empty map.
  • The postgres-exporter sidecar has no readiness probe: an unready sidecar would take the database out of its Service.
Start-up

From scheduled to serving

stock-app's pod runs an init container, migrate, before the app: it applies the database schema with Alembic and must exit 0, so the app never starts against an old schema. The app then waits for its readiness probe before any traffic arrives.

Resources

Requests, limits and what happens at the limit

Requests schedule

The scheduler places a pod only on a node with enough unrequested CPU and memory. Requests are a reservation, not a cap: stock-app asks for 192Mi because pandas and yfinance need that much just to start.

Limits enforce

Above its CPU limit a container is throttled; above its memory limit it is OOM-killed and restarted. Grafana was killed at 512Mi with dashboards refreshing, so it now has 1Gi and GOMEMLIMIT, which makes Go collect garbage harder before it reaches the limit.

QoS classes

Requests equal to limits make a pod Guaranteed; lower requests make it Burstable (every pod here); none at all, BestEffort. Under memory pressure the kubelet evicts BestEffort pods first, Guaranteed last.

Every workload here sets requests and limits; the hardening scorecard checks it live. What the cluster can't show you yet is actual usage: kubectl top needs metrics-server, which kind doesn't install.

Rollouts

A config change rolls out new pods

Config files such as prometheus.yml or Grafana's datasources.yaml are plain files next to the manifests. A kustomization.yaml turns each into a ConfigMap and adds a hash of the content to its name. A changed file means a new name, so the pod template changes and the Deployment rolls out.

The exception: Prometheus

This site reads prometheus-config by name to learn which namespaces are scraped, so that ConfigMap keeps a fixed name and no rollout happens. Prometheus re-reads the file itself (--config.auto-reload) once the kubelet has updated the mounted copy, within about two minutes. It skips a broken file and reports prometheus_config_last_reload_successful 0, and that file would then fail its next start.

What each change costs

  • Grafana: a new pod, so you log in again.
  • Tempo: a new pod, so its traces are gone.
  • OpenTelemetry Collector: a new pod; spans buffered in the app's SDK are retried.
  • Prometheus: nothing, if the file is valid.

Hands on

Try it

Scale out and back; the Cluster map shows where each new pod lands.

kubectl scale deploy/traffic-generator -n apps --replicas=3
kubectl scale deploy/traffic-generator -n apps --replicas=1

Roll out a restart and watch a new ReplicaSet replace the old one.

kubectl rollout restart deploy/stock-ui -n apps
kubectl rollout status deploy/stock-ui -n apps
kubectl get rs -n apps -l app=stock-ui
kubectl rollout history deploy/stock-ui -n apps

Make stock-app unready without restarting it: stop the database and watch the dot on the Overview turn orange.

kubectl scale statefulset/timescaledb -n data --replicas=0
kubectl get endpointslices -n apps -l kubernetes.io/service-name=stock-app-service --watch
kubectl scale statefulset/timescaledb -n data --replicas=1

Interview check

Questions to answer from this chapter

Readiness, liveness and startup probes: what does each control?

Readiness decides whether the pod is an endpoint of its Services. Liveness decides whether the kubelet restarts the container. A startup probe holds off both until a slow starter is up, instead of a huge initialDelaySeconds. A liveness probe should check only the process itself, never its dependencies.

A pod is in CrashLoopBackOff. How do you find out why?

kubectl describe pod for events and the last state (exit code; 137 means killed, often OOM), kubectl logs --previous for the crashed run, then the probes, the limits and missing config or Secrets. The back-off grows to five minutes between attempts.

How does a rolling update avoid downtime, and when doesn't it?

It creates new pods (up to maxSurge) and removes old ones only as new ones turn ready (keeping within maxUnavailable). It fails to protect you when readiness doesn't reflect real readiness, when old and new versions can't run side by side (schema changes), or when connections are cut without a graceful shutdown (a preStop hook and enough terminationGracePeriodSeconds).

Why run database migrations in an init container, and what is the risk?

The schema is in place before the app starts, and a failed migration stops the rollout. With several replicas, every pod runs it, so migrations must be idempotent and safe to run concurrently (Alembic takes a lock); many teams prefer a separate Job that the rollout waits for.

When would you choose a DaemonSet over a Deployment?

When you need exactly one pod per node because the work is per node: node-exporter, log shippers, CNI agents, kube-proxy. A Deployment places replicas wherever there is room and gives no per-node guarantee.
