Design decisions

What this cluster chose and why. Every change follows these decisions and conventions; a change that needs a different one updates this page in the same pull request.

Decisions

What we chose

  • Ownership. A resource owned by one component lives in <component>/k8s/. Cluster-wide resources (kind config, the Gateway API controller and the shared Gateway, cert-manager and the cluster's CA, namespaces, RBAC) live in platform/ and are applied first. If deleting a component should delete a resource, it belongs to the component.
  • Entry point. Gateway API, implemented by Envoy Gateway (platform/envoy-gateway/). The platform owns the GatewayClass and the one shared Gateway (platform/gateway/); each component owns its HTTPRoute. Only namespaces labelled shared-gateway-access: "true" may attach routes. kind maps host ports 80 and 443 to the fixed NodePorts 30080 and 30443 of the Gateway's Envoy Service, so the proxy needs no node pinning. Every hostname answers on HTTP and on HTTPS; TLS ends at the Gateway, and pods serve plain HTTP. How it works.
  • Certificates. cert-manager (platform/cert-manager/) issues every certificate from the cluster's own CA, the ClusterIssuer sample-cluster-ca: a certificate is a Certificate object, never a file a script makes. The Gateway's certificate lists each hostname, because a *.localhost wildcard is rejected. How.
  • Namespaces. apps (stock-app, traffic-generator, stock-ui), monitoring, vault, data (TimescaleDB) and docs (this site). Every manifest sets its namespace; cross-namespace calls use <service>.<namespace>.
  • Least privilege. Each workload has its own ServiceAccount, with no API token unless it needs one: Prometheus (service discovery, kubelet metrics), the documentation site (the live diagrams) and the OpenTelemetry Collector (pods in apps, to label spans) get read-only API access. Vault may check tokens (TokenReview) and keep its unseal key in one Secret in its own namespace; no other workload of the project can read Secrets. Live view.
  • Metrics discovery. A Service is scraped when annotated prometheus.io/scrape: "true" and prometheus.io/job: <name> (optionally prometheus.io/port and prometheus.io/path), so a new service needs no Prometheus change. Each node's kubelet is scraped too (job kubelet), for the CPU and memory of nodes, pods and containers. A new namespace must be added to the scrape list in prometheus.yml.
  • Alerting. Alert rules live in alerts.yml next to prometheus.yml, each with a severity label. Prometheus evaluates them and sends firing alerts to Alertmanager, whose only receiver sends nothing: alerts are read in its UI and in Grafana. How.
  • Tracing. stock-app traces every HTTP request with OpenTelemetry and sends it over OTLP to the OpenTelemetry Collector, which adds Kubernetes metadata and forwards it to Tempo; Grafana reads Tempo. Apps only know the Collector's address. The latency histogram's exemplars and the service's own log lines carry the trace ID.
  • Secrets. Development credentials live in one Secret per tool. Secrets can't cross namespaces, so the database password is declared in both namespaces that need it. Vault holds the apps' secrets, one path per service (services/<service>/). Apps sign in to Vault with their ServiceAccount (kubernetes auth method) and get a token for their own path only; the root token is for people and Vault's setup hook. How.
  • Stateful data. TimescaleDB and Vault (Raft storage) keep their data on PVCs, which are empty after every ./recreate-cluster.sh; that is fine because stock-app refills the database from the provider and Vault holds only demo secrets. Setup that a restart can undo runs on every start, never once in a Job: Grafana loads its dashboards and datasources from ConfigMaps, and Vault, which restarts sealed, unseals itself with the key it keeps in a Secret and applies its KV mounts, auth method and policies in a postStart hook. Grafana's database (logins, preferences) is on an emptyDir.
  • API contract. stock-app's openapi.yaml is the source of truth; its models are generated from it.
  • Documentation. This site is the only documentation: the root README.md just points here. One Go service, documentation/, serves the pages and their live data: the cluster map from the Kubernetes API (informers, read-only RBAC) and read-only PromQL forwarded to Prometheus. Pages are hand-written HTML with shared JavaScript modules and no build step. GitHub Pages publishes the same files, which then render a recorded snapshot. Reader comments are GitHub issues labelled docs-feedback, created and closed in the reader's name: the service runs GitHub's sign-in for a GitHub App and keeps the reader's token in Vault, so the browser never holds it. How.
  • Dependency updates. Renovate opens update pull requests daily. Minor, patch and digest updates merge automatically when CI is green; majors and language runtimes wait for a human. Releases must be three days old; local :dev images are ignored. Details.
Conventions

How things are named and built

  • Deployment and app label = the component's name; Service <component>-service (a StatefulSet's serviceName is a second, headless one, <component>-headless); HTTPRoute <component>-route; ServiceAccount <component>.
  • Every workload has requests, limits and a readiness probe; own images run as non-root; every image is pinned (base images and GitHub Actions by digest).
  • A config file a container reads (e.g. prometheus.yml) is a plain file in k8s/; a kustomization.yaml turns it into a ConfigMap, and ./recreate-cluster.sh applies such directories with kubectl apply -k. Kustomize adds a hash of the content to the ConfigMap's name, so a changed file rolls out new pods. Only prometheus-config keeps a fixed name (the documentation site reads it by name); Prometheus re-reads it itself (--config.auto-reload).
  • ./recreate-cluster.sh is the single entry point and stays idempotent.
  • Each fact is written on one page of this site; other pages link to it. A new page goes into PAGES in documentation/web/site/assets/js/site.js.
