Reference · build and ship

From a clean laptop to a tested cluster

One script builds the whole cluster, three layers of tests check it, and CI runs the same steps on every pull request, including a real kind cluster. Renovate keeps every pinned version moving.

Deploy

What ./recreate-cluster.sh does

The single entry point. It deletes the cluster, recreates it, deploys every component in dependency order and fails loudly, printing events and the logs of unready pods, if anything doesn't come up. Running it again is always safe. Each step below is checked against the cluster as it is now.

    Before deleting anything, the script stops if kind is not v0.33.x (it decides the Kubernetes version) or if something else holds host port 80 or 443 (Run it).

    CI

    What runs on every pull request

    Four GitHub Actions workflows run on every pull request and on main. The e2e job builds a real kind cluster with generated prices, runs the suite, then restarts the Gateway's Envoy proxy and checks that *.localhost still answers, wherever the new pod lands. Pushes to main that touch this site publish it to GitHub Pages, where it shows a recorded snapshot.

    Dependencies

    Every version pinned, every pin updated

    Images, Go modules, Python and npm packages, pre-commit hooks, GitHub Actions, the Envoy Gateway and cert-manager releases, kind in CI and golangci-lint are all pinned. Tags can be moved, so Dockerfile base images and GitHub Actions are pinned by digest, with the tag kept as a label (python:3.14-slim@sha256:…, actions/checkout@… # v6.1.0); the cluster's images use exact release tags. Renovate (renovate.json) opens update pull requests every day.

    • Minor, patch and digest updates merge automatically once CI is green; the e2e job deploys the whole cluster, so a broken image can't sneak in.
    • Major updates and new language runtime versions (Python, Go, Node) wait for a human, because their versions are also set in the workflows. A new digest of the same base-image tag merges automatically.
    • A release must be three days old; the local :dev images are ignored.
    • Renovate runs as the Mend Renovate GitHub App: Mend, the company behind Renovate, hosts it for free, so no workflow is needed. Run logs: developer.mend.io.
    Extend

    Add a component

    Copy an existing component (stock-app/ for a Python service, documentation/ for Go), then:

    1. codeA Dockerfile with a base image pinned by digest that runs as non-root. Go needs go.mod, Python needs tox.ini: the Makefile finds them. A Vite frontend goes into FRONTENDS in the Makefile.
    2. kubernetesIn my-service/k8s/ (namespace apps): Deployment my-service, Service my-service-service, HTTPRoute my-service-route for my-service.localhost (add that hostname to platform/gateway/certificate.yaml too, or HTTPS fails for it), and ServiceAccount my-service with automountServiceAccountToken: false; requests and limits, a readiness probe and a non-root securityContext (conventions).
    3. cluster scriptAdd it to IMAGES, COMPONENTS and URLS in recreate-cluster.sh.
    4. metricsAnnotate the Service with prometheus.io/scrape: "true" and prometheus.io/job (plus port or path when needed); add a dashboard JSON with a fixed uid to monitoring/grafana/k8s/dashboards/ and list it in that directory's kustomization.yaml.
    5. testsAdd its URL to SERVICE_URLS in e2e/cluster.py, and e2e tests for what it does.
    6. docsA section on Components with a live spec sheet (<dl class="spec" data-app="my-service">), a one-line purpose in assets/js/catalog.js, and a place in the architecture diagram (assets/js/architecture.js). Until it has one, the Overview lists it under the diagram. If it calls another service through an address in a config file rather than an env var, add the pair to REFERENCES in documentation/k8s/documentation-deployment.yaml so the map draws the line.
    7. verifymake lint test-unit && ./recreate-cluster.sh && make test-e2e
