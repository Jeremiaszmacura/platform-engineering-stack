Reference · build and ship

From a clean laptop to a tested cluster

One script builds the whole cluster, three layers of tests check it, and CI runs the same steps on every pull request, including a real kind cluster. Renovate keeps every pinned version moving.

Deploy

What ./recreate-cluster.sh does

The single entry point. It deletes the cluster, recreates it, deploys every component in dependency order and fails loudly, printing events and the logs of unready pods, if anything doesn't come up. Running it again is always safe. Each step below is checked against the cluster as it is now.

    Your kind decides the Kubernetes version: kind v0.33 creates 1.37 nodes, as CI does. An older kind silently creates an older cluster, and can't load images into a newer one.

    Tests

    Three layers of checks

    CommandRuns
    make test-unitGo (go test) and Python (tox -e tests) unit tests, found by go.mod and tox.ini; for this site that includes a check of every link between pages
    make lintgolangci-lint, then pre-commit (black, bandit, YAML and JSON checks), stock-app's import rules and API-model drift check
    make build-frontend test-unit-frontendboth Vite frontends, their Vitest tests, and this site's JavaScript tests (node --test)
    make test-e2epytest in e2e/ against the running cluster, over HTTP only

    The end-to-end tests cover every *.localhost URL, this site's map, RBAC and Prometheus proxy, Vault secrets, CORS for both frontends, every stock-app endpoint validated against its published /openapi.yaml, the cache-aside flow, the Prometheus and Grafana pipeline, and request traces in Tempo. stock-app calls Yahoo Finance by default; to test without it, deploy with STOCK_PROVIDER=fixture and skip the tests marked external:

    make test-e2e E2E_PYTEST_ARGS='-m "not external"'   # what CI runs
make test-e2e E2E_PYTEST_ARGS='-k stock'            # scope with -k

    CI

    What runs on every pull request

    Four GitHub Actions workflows run on every pull request and on main. The e2e job builds a real kind cluster with recorded prices, runs the suite, then restarts the Gateway's Envoy proxy and checks that *.localhost still answers, wherever the new pod lands. Pushes to main that touch this site publish it to GitHub Pages, where it shows a recorded snapshot.

    Dependencies

    Every version pinned, every pin updated

    Images, Go modules, Python and npm packages, pre-commit hooks, the Envoy Gateway release, kind in CI and golangci-lint are all pinned. Renovate (renovate.json) opens update pull requests every day.

    • Minor, patch and digest updates merge automatically once CI is green; the e2e job deploys the whole cluster, so a broken image can't sneak in.
    • Major updates and language runtimes (Python, Go, Node) wait for a human, because their versions are also set in the workflows.
    • A release must be three days old; the local :dev images are ignored.
    • Renovate runs as the Mend Renovate GitHub App: Mend, the company behind Renovate, hosts it for free, so no workflow is needed. Run logs: developer.mend.io.
    Extend

    Add a component

    Copy an existing component (stock-app/ for a Python service, documentation/ for Go), then:

    1. codeA Dockerfile with a pinned base image that runs as non-root. Go needs go.mod, Python needs tox.ini: the Makefile finds them. A Vite frontend goes into FRONTENDS in the Makefile.
    2. kubernetesIn my-service/k8s/ (namespace apps): Deployment my-service, Service my-service-service, HTTPRoute my-service-route for my-service.localhost, and ServiceAccount my-service with automountServiceAccountToken: false; requests and limits, a readiness probe and a non-root securityContext (conventions).
    3. cluster scriptAdd it to IMAGES, COMPONENTS and URLS in recreate-cluster.sh.
    4. metricsAnnotate the Service with prometheus.io/scrape: "true" and prometheus.io/job (plus port or path when needed); add a dashboard JSON with a fixed uid to monitoring/grafana/k8s/dashboards/ and list it in that directory's kustomization.yaml.
    5. testsAdd its URL to SERVICE_URLS in e2e/cluster.py, and e2e tests for what it does.
    6. docsA section on Components with a live spec sheet (<dl class="spec" data-app="my-service">), a one-line purpose in assets/js/catalog.js, and a place in the architecture diagram (assets/js/architecture.js). Until it has one, the Overview lists it under the diagram.
    7. verifymake lint test-unit && ./recreate-cluster.sh && make test-e2e
