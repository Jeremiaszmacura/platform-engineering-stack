Networking basics

Three address ranges

Kubernetes networking is easier once you separate these three ranges. They never overlap, and each one is managed by a different component.

A pod IP changes every time the pod is recreated. A Service's ClusterIP and DNS name stay the same for as long as the Service exists. Apps should always call the Service name, never a pod IP.

Request journeys

Traffic from outside into the cluster is called north-south. Traffic between pods is called east-west. Each trace follows one real request, using the addresses in your cluster right now.

How Prometheus gets its permissions


# monitoring/prometheus/k8s/prometheus-serviceaccount.yaml
ServiceAccount  monitoring/prometheus            # token mounted (default)
# platform/rbac/prometheus.yaml (cluster-scoped, so it lives in platform/)
ClusterRole     prometheus   get/list/watch  nodes, services, endpoints, pods
                             get             /metrics (non-resource URL)
ClusterRoleBinding prometheus  → ServiceAccount monitoring/prometheus

      
Kubernetes mounts the token at /var/run/secrets/kubernetes.io/serviceaccount/token (the kube-api-access-* volume this page uses to detect tokens). Prometheus uses it to call the API server at kubernetes.default.svc. You can check what each identity is allowed to do yourself:


kubectl auth can-i list pods   --as=system:serviceaccount:monitoring:prometheus -A   # yes
kubectl auth can-i get secrets --as=system:serviceaccount:monitoring:prometheus -n apps   # no
kubectl auth can-i list pods   --as=system:serviceaccount:apps:go-app -n apps   # no

      
Two ways to turn the token off. This repo sets automountServiceAccountToken: false on the ServiceAccount, so every pod using it starts without a token. You can also set the same field on a pod spec, and the pod setting wins. Without either, even a pod with no RBAC permissions carries a token an attacker could use to explore the API.

      
Vault tokens are a different kind of identity. go-app and stock-app sign in to Vault with VAULT_TOKEN, the dev root token, not with their ServiceAccount. The usual production setup is Vault's Kubernetes auth method: Vault checks the pod's ServiceAccount token and gives back a short-lived token limited to that service's path.

    

  


  

    

      Configuration
      
Secrets and ConfigMaps

      
A pod can only reference Secrets in its own namespace. That is why the same Secret name or value can appear in two namespaces: one copy for the server and one for its client. Only key names are shown, never values.

    

    

      

        
ObjectNamespaceKeysConsumed byHow

        
      

    

    
These Secrets are written with stringData in plain text and committed to Git. That's fine for a dev cluster and never acceptable anywhere else. Kubernetes Secrets are only base64-encoded, and etcd stores them unencrypted unless you enable encryption at rest. In real clusters, use the External Secrets Operator, Sealed Secrets, or the Vault Agent / CSI driver.

    
Env vars filled from a Secret are read once, when the container starts. If the Secret changes, the pod keeps the old value until it restarts. A ConfigMap mounted as a volume does update inside the pod after a short delay, but Prometheus only reloads its config when told to (/-/reload with --web.enable-lifecycle, or a restart).

  


  

    

      State
      
Storage: real disks and scratch dirs

    

    

      

      
WaitForFirstConsumer (kind's default StorageClass) means the volume is created only after the scheduler picks a node for the pod. A local-path volume is a directory on that node, so from then on the pod can only run there. If that node goes down, the data can't move. Network storage (EBS, Ceph, NFS) avoids that.

      
A PVC outlives its pod, so deleting the pod keeps the data. It does not outlive kind delete cluster, which ./recreate-cluster.sh runs.

      
emptyDir volumes are scratch directories deleted with the pod. stock-app needs them because it runs with readOnlyRootFilesystem: true. hostPath volumes expose the node's own files: node-exporter reads /proc, /sys and / to report on the node.

      
Grafana and Vault have no volume at all. Grafana keeps dashboards and the datasource in a SQLite file inside the container, so a restarted pod loses them until you run the Ansible playbook again. Vault in dev mode keeps everything in memory, so a restart loses every secret and the services/ and infra/ mounts. The finished vault-configure Job does not run again by itself.

Probes

      
A readiness probe decides whether a pod is listed as an endpoint of its Service, so whether it gets traffic. A liveness probe decides whether the kubelet restarts it. Select a pod on the map to see its probes. Some pods have only a readiness probe on purpose: stock-app's /health checks the database, and an outage there should not restart the app. Vault would lose every secret on a restart.
